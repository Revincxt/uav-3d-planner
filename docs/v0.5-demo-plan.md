# v0.5 complex-city demonstration protocol

## Scope

Version 0.5 is a presentation and trajectory-post-processing study. It asks whether the existing
reactive and schedule-aware planners remain inspectable in richer urban geometry, and whether a
shared geometric post-processor can remove visually abrupt lattice turns without weakening the
project's explicit time and collision contracts.

The study is curated, deterministic, non-preregistered, and non-confirmatory. Its scenarios are
accepted from their constructors and metadata only; planner outcomes are forbidden as a selection
criterion. Results must not be pooled with v0.4 because the cohort geometry, horizon, work budget,
and trajectory post-processing protocol differ.

## Scenario contract

The public cohort contains one calibration case and seven complex-city cases. Complex cases share
a declared city volume but vary start and goal axes, street layouts, building footprints and
heights, static no-fly volumes,
temporary restrictions, and moving-obstacle schedules. The public manifest records the declared
district, street pattern, cohort, event family, case ID, and semantic problem fingerprint.

The cohort remains a diagnostic set. Labels such as `demo` and `diagnostic` describe intended use;
they are not train, validation, or held-out test partitions.

## Raw and certified trajectories

Every run retains the planner's original `rawTimedPath`. A common deterministic post-processor:

1. splits the path at explicit wait actions;
2. preserves the start, goal, wait positions, wait durations, and total time;
3. constructs rounded candidates within movement-only blocks;
4. maps candidate samples back to the block's original time progress;
5. rejects any candidate that exceeds the declared speed ceiling; and
6. accepts a candidate only when every resulting linear space-time segment passes the same
   continuous collision predicate used by the execution audit.

The accepted `timedPath` is therefore still an ordinary piecewise-linear `TimedPath`; it is not an
uncertified browser spline. If every rounded candidate fails, the record explicitly reports a raw
fallback. The method improves geometric turn appearance but does **not** certify aircraft attitude,
acceleration, jerk, or a full dynamics model.

## Web record contract

The v2 browser bundle stores each raw and certified path once. Frames contain only time-local
vehicle, restriction, obstacle, and event state; path prefixes and suffixes are derived in the
browser. This keeps record size linear in trajectory length while supporting continuous-time
interpolation between semantic event frames.

The page must expose raw-versus-certified comparison, the active layer set, view orientation,
continuous trace time, event context, and the declared smoothing outcome. Visual interpolation may
only follow the exported certified polyline and may never invent an unaudited spatial curve.

## Interpretation boundary

The common post-processor is downstream of planning. A shorter-looking or smoother displayed path
is not evidence that one planner searched better, predicted better, or used less compute. Planner
work counters keep their algorithm-specific units, and the UI must not normalize or rank unlike
units. Failures and raw fallbacks remain visible rather than being filtered from the public cohort.
