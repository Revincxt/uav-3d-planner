## Experiment overview

- **Title:** Separating planner output, geometry post-processing, and a retimed execution candidate
- **Objective:** Test whether deterministic time reparameterization can satisfy a frozen discrete
  execution envelope without obscuring the original planner outcome or the continuous space-time
  collision audit.
- **Hypothesis:** Local duration extension will reduce discrete climb-rate and acceleration-proxy
  violations for some recorded paths, but dynamic conflicts and the 90 s mission limit will leave
  some candidates explicitly unqualified.
- **Type:** Deterministic simulation and reproducibility validation

The envelope is a benchmark contract, not a vehicle model or flight-feasibility certificate. It
does not model attitude, thrust, curvature-continuous dynamics, jerk, wind, energy, or actuators.

## Frozen study matrix

- 10 existing v0.6 scenarios; no outcome-based additions or removals;
- 4 unchanged planning conditions per scenario;
- 40 deterministic planner runs;
- scenario remains the independent unit (`n = 10`), not the 40 planner-condition rows;
- protocol ID `predictive-space-time-v4` and schema version 3;
- dataset ID `predictive-execution-envelope-v0.7`.

Version 0.6 is a paired historical baseline. Its rows are not pooled with v0.7 as independent
observations. Because no planner implementation changes in v0.7, raw paths and raw planner metrics
must remain attributable to the original planning conditions.

## Declared discrete envelope

| Parameter | Frozen value |
| --- | ---: |
| Maximum segment-average speed | 8.0 m/s |
| Maximum absolute segment-average climb/descent rate | 3.0 m/s |
| Maximum adjacent-segment acceleration proxy | 4.0 m/s² |
| Reversal threshold | 150° |
| Allowed non-zero-speed reversals | 0 |
| Maximum execution-candidate arrival time | 90.0 s |

The evaluator records `continuousDynamicsCertified = false`. Thresholds are fixed before the
v0.7 bundle is regenerated and are not relaxed to increase the qualified count.

## Three-stage evidence contract

1. `rawTimedPath` is the planner or online-policy result.
2. `geometryCandidate` is the common rounded geometry under its original timing and collision
   audit.
3. `executionCandidate` is an optional deterministic retiming of that geometry. It is published
   only when it satisfies the discrete envelope, remains within the mission-time limit, and passes
   the continuous space-time collision audit after all timestamps change.

Wait durations are preserved, but later absolute timestamps may move. A failed retiming never
silently falls back to an execution-qualified path. The raw and geometry evidence remain available.

## Metric domains

- `plannerMetrics` are computed only from `rawTimedPath`: planner success, failure, arrival, wait,
  raw length, raw minimum dynamic separation, replans, and algorithm-specific work.
- `geometryMetrics` are recomputed only from the collision-certified geometry candidate; its
  path-length or clearance changes are common post-processing outcomes, not planner outcomes.
- `executionMetrics` describe only the optional execution candidate: qualification status, failure
  reason, arrival, duration stretch, path length, collision result, envelope result, and minimum
  dynamic separation.
- Work units remain algorithm-specific and are never normalized into a cross-family ranking.

## Expected outputs and acceptance

| Output | Path | Success criterion |
| --- | --- | --- |
| Predictive JSON bundle | `web/public/predictive-data.json` | Schema-v3, exactly 10 scenarios and 40 runs |
| CSV projection | `web/public/predictive-records.csv` | Explicit planner/execution field prefixes |
| Scenario manifest | `web/public/predictive-scenario-manifest.json` | Deterministic IDs, hashes, and zero outcome filtering |
| Academic Web view | `web/predictive.html` | Raw/geometry/execution semantics and witness evidence remain distinct |

Required gates:

- every raw path retains exact endpoints and reproduces its planner-domain metrics;
- every non-null execution candidate has strictly increasing timestamps, preserves wait durations,
  satisfies every declared envelope limit, and passes the continuous space-time audit;
- every failed candidate records one explicit status and remains null;
- planner success is unchanged by downstream qualification failure;
- the public UI can jump to the recorded closest-approach witness and labels exact versus
  approximate methods without relying on color alone;
- Python reruns, committed-data validation, TypeScript validation, unit tests, and the production
  Web build all pass.

The number of qualified execution candidates is an observed result, not a release gate.
